# Round 7: persistent workers, the record fast path, and the SIMD int-run spike

Three independent changes, measured on a shared machine (Ryzen 7 5800X). Wall
is the median of three runs of 2000 loads; instructions per load come from
`perf stat -e instructions` on `build-release/tools/bench/bench_load <file>
2000 <threads>`, `1` being the serial path and `0` the default.

## Task A — persistent workers

Per-load instructions are unchanged (the same parse work, and the files below
the old threshold stayed serial), which is expected: this task removes the
per-load `std::thread` start-up and the per-chunk schema copies, both of which
are wall/task-clock costs, not instruction-count costs.

## Task B — record fast path

A record made only of plain numbers/time (no CHAR, no ISO_TIME_RANGE) and
ending on a comma or the single-character marker is walked slot by slot; any
other byte rewinds the columns and the unchanged state machine parses that
record, so messages, lines and record numbers are still its.

| file | instr serial before/after (M) | instr default before/after (M) | wall serial before/after |
|---|---|---|---|
| C1_PP_DWP | 5.074 / 4.259 (-16.1%) | 5.324 / 4.510 (-15.3%) | 0.30 / 0.25 ms |
| C4_CP_AUX_ESOC_MEP | 5.708 / 5.562 (-2.6%) | 6.001 / 5.857 (-2.4%) | 0.33 / 0.30 ms |
| C1_CP_EDI_MP | 3.976 / 3.329 (-16.3%) | 4.124 / 3.476 (-15.7%) | 0.24 / 0.20 ms |
| C3_CP_PEA_LERL_DEFlux | 34.435 / 29.886 (-13.2%) | 35.235 / 30.690 (-12.9%) | 1.92 / 1.64 ms |
| C1_CP_CIS-CODIF_HS_H1_CS | 103.886 / 100.112 (-3.6%) | 105.853 / 102.092 (-3.6%) | 5.30 / 5.00 ms |

The two decisions that made it pay everywhere were the signed <=4-digit
shortcut (CSA writes fills as `-1`) and avoiding `string_view::substr` per
value. `benchmark.py --runs 21` on the shared machine: 13.0 -> 13.5 ms total
(wall noise; per-file median 1.53x -> 1.48x, min 1.11x -> 1.17x).

Differential fuzzing (`tools/fuzz/fuzz_records_diff`, oracle
`tools/fuzz/reference_records.hpp`): 5.2M runs in 20 minutes, clean.
`fuzz_load` corpus replay and 160k runs in 10 minutes, clean.

## Task C — SIMD integer runs (spike, reverted)

Implemented per Muła (`0x80.pl/notesen/2018-04-19-simd-parsing-int-sequences.html`):
an SSE4.1 kernel that loads 16 bytes, builds the digit/comma/space masks, looks
up a shuffle pattern for four 4-digit-padded spans, and converts with
`pshufb` + `pmaddubsw` + `pmaddwd`. Dispatch was compiler-attribute based and
header-only (`__attribute__((target("sse4.1")))`, chosen once with
`__builtin_cpu_supports`), with a 128-entry thread-local pattern cache keyed on
the digit and comma masks; scalar elsewhere.

The header-only dispatch scheme compiled cleanly with both GCC 16 and clang 21.
An AVX2 variant was not added: the conversion is a 16-byte lane-local kernel
and AVX2 would only run two windows at once, not change the per-window cost.

DWP is the target (26 consecutive INT slots):

| | instructions/load | wall (min) |
|---|---|---|
| Task B | 4.259 M | 0.25 ms |
| Task B + SIMD run | 4.370 M (+2.6%) | 0.28 ms (+12%) |

Profiles put 23% of DWP in the SIMD parser and 12% in the run plumbing, against
~12% for the scalar `std::from_chars` path it replaces: DWP's values are 1-3
digits, so the mask/cache/shuffle overhead per window is larger than four cheap
scalar parses, and many windows are rejected when the run reaches a sign or the
FLOAT columns. It fails the "DWP >= 5% better and no file worse" bar, so the
implementation was reverted; only the Task B commit stands. The full Muła
lookup table (65536 records, ~2.5 MiB) is also not something a header-only
library should ship, which is the structural reason this stays out.

## Instruction diet (after round 7)

Instructions per serial load (`bench_load <file> 1000 1`), round 7 end (`aba30e9`) -> `7c0d20e`:

| file | round 7 | diet | change |
|---|---|---|---|
| C1_PP_DWP | 4.264M | 3.644M | -14.5 % |
| C4_CP_AUX_ESOC_MEP | 5.567M | 4.635M | -16.7 % |
| C1_CP_EDI_MP | 3.334M | 2.652M | -20.5 % |
| C3_CP_PEA_LERL_DEFlux | 29.887M | 18.546M | -37.9 % |
| CODIF H1 | 100.117M | 68.488M | -31.6 % (cycles 24.9M -> 13.3M) |

Steps, each measured alone:

1. Fill cells matched on the raw text before parsing, first byte kept in the column (`fill_first`).
   Without that byte the full compare ran per value and cost +4 % instructions.
2. One-loop integer parser and Clinger's fast path for decimals (`parse_plain_int`,
   `parse_plain_decimal`, `values.hpp`): equal to `std::from_chars` / fast_float whenever they
   accept, checked by `fuzz_float` (105M runs). Without exponent support, PEA (44 % of values
   like `1.234e-05`) was parsed twice and got +21 %; with it, -13 %.
3. The fast path walks a record column by column: one type switch per column, a typed loop per
   value. CODIF -17 %, PEA -14 %.
4. `[[gnu::flatten]]` on the typed loop: CODIF -17 % instructions, -37 % cycles.

Reverted: an inline "spaces only" padding skip before the out-of-line `skip_blanks` (CODIF +10 %,
PEA +5 %: it changed GCC's inlining of the whole loop). That fragility is why step 4 asks for
inlining explicitly.

`fuzz_records_diff` used to generate `SIZES = 1` only, so multi-value columns were never fuzzed;
it now gives each variable 1-4 elements. A planted bug (a multi-value column's second value stored
twice) is caught within seconds. A planted bug that only makes the fast path bail out is not
caught, by design: the state machine then produces the right answer.

Still left: DWP's header (~40 % of its load) and ~115 instructions per value on CODIF's `0,`.
