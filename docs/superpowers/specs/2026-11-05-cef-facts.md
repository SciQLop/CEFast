# CEF-2 facts (DS-QMW-TN-0010 iss.2 rev.0.5; CEFLIB 1.8.6)

**Q1 order/shape.** §2 (p.3) "natural C ordering, and one entry is required for each element"; §2.9
(p.13) "the last index varies the fastest". For SIZES=a,b,c the record position is i*b*c + j*c + k
(c fastest, then b, then a). CEFLIB `Compute_numpy_sizes` (PYTHON/src/ceflib.c:440-462) appends
`size[0..]` in declared order after the record dim, so numpy shape is **(nrec,a,b,c), C-contiguous** —
same indexing as the record. ISO_TIME_RANGE appends a trailing 2 *after* SIZES (ceflib.c:526-530) →
(nrec,a,b,c,2). Non-varying: (a,b,c), no record dim; SIZES=1 with one element is scalar → (nrec,)
(`IS_SCALAR` ceflib.c:21,:465).

**Q2 INCLUDE lookup.** `Search_path` (C/src/CEF.c:292-326): (1) the name as written, i.e. relative to
the **current working directory** — not the including file's directory; (2) each dir in **`$CEFPATH`**
split on `PATH_SEPARATOR` (`:`, or `;` on Windows); empty result = not found. Spec §2.5 only says the
reader must locate it and that "path information should not be given inside the cef file".
**Q3 continuation.** §2.3 (p.4-5): `\` after a comma in a value list, "all text beyond the `\` is
ignored and the next line is concatenated"; "may NOT be used within a quoted text string as they will
be treated verbatim". Same for `DATA` lists (§2.7 p.9). So yes, `DATA = a, b, \` continues. CEFLIB
implements it **only in Parse_variable** (CEF.c:1331-1335: while last char is `\`, read the next line
over it); globals and metadata blocks do not continue.

**Q4 quoting/escaping.** `"…"` text is verbatim; white space and commas inside are data (§2 p.3, §2.7
ENTRY p.7, CHAR "must be enclosed in double quotes" §2.7 p.10). There is **no escape mechanism** — no
`\"`, no doubled quotes: CEFLIB copies to the next `"` (CEF.c:136-143) and fails on an unterminated
quote, so an embedded quote cannot be represented. Unquoted tokens stop at white space, `,` or `!`
(CEF.c:147), so an unquoted CHAR cannot hold a space or comma.
**Q5 comments.** §2 (p.1): "An exclamation mark is used as a comment marker, and all input to the
right of this marker up to the newline character is ignored on input" — unqualified, so header and
data lines alike. CEFLIB is quote-aware: `!` inside a quoted value is kept (Get_token tests QUOTES
first, CEF.c:136-146) and whole-line comments are skipped (CEF.c:895). After data values a trailing
`! …` ends that line's token loop (Get_token returns NULL on `!`, CEF.c:134); a comment *inside* a
multi-line record silently drops the rest of that line — only the total count check (Q8) notices.

**Q6 white space.** Insignificant outside quotes: "white space surrounding delimiters is ignored" and
all `\r`,`\n`,tabs "at the start and end of records and surrounding delimiters are to be deleted"
(§2 p.3, §2.4 p.5). CEFLIB trims trailing white space before comparing the record marker
(CEF.c:906-918, so `…, 1.0 $` is fine). Significant only inside quoted strings.
**Q7 ISO time grammar.** `yyyy-mm-ddTHH:MM:ss.wwwZ` (§2.1 p.3), "strict ISO format adopted by CSDS";
§2.1.1 any number of fractional digits, trailing `Z` retained. Seconds are mandatory: date-only and
`…T11:13Z` are **not** valid, and only `Z` is allowed (no offsets). `T`/`Z` case-insensitive (p.2).
CEFLIB requires the literal `-`,`-`,`T`,`:`,`:`,`Z` at fixed positions and returns -1…-6 otherwise
(LIB/src/TIMES.c:402-465); callers ignore the return (CEF.c:944), so a malformed time becomes
`-1.0` ms, not an error. No calendar validation (month 99 accepted).

**Q8 short records / trailing comma.** Trailing fields may not be dropped: "Missing entries must be
padded by a fill value" (§2.9 p.13), "one entry is required for each element" (§2 p.3). CEFLIB reads
on across lines until the element count is met, then checks `nb_values == root.nb_values` and errors
"Record %d : %d/%d valeurs lues" (CEF.c:993-997) — a short record first swallows the next line. A
trailing comma before the marker is tolerated (separator consumed, then end-of-line, CEF.c:158-176)
although "delimiters must be separated by valid input" forbids an empty field: tolerating is safe,
silently skipping an empty field is not.
**Q9 other parse-affecting keywords.** `END_OF_RECORD_MARKER` — delimiter, default `\n`, stripped only
after trailing white space is trimmed (§2.4). `DATA` — its *presence* marks a non-record-varying
variable whose values live only in the header (§2.7). `DEPEND i` and `DELTA PLUS/MINUS` — values may
be the *name of a variable in the file* instead of a literal; DELTA is in seconds (§2.7.2), and any
metadata value may name a variable (§2.3 p.4). `VALUE_TYPE` — in a global block it retypes every
*subsequent* `ENTRY` until reset or block end (§2.6 p.7); in a variable block it types the whole
variable. `SIZES` (count and order), `INCLUDE` (may appear inside a metadata block, §2.5). Nothing
else affects tokenization: REPRESENTATION i, TENSOR ORDER, SCALETYP, SIG_DIGITS, FILLVAL, CATDESC,
SCALMIN/MAX are interpretation-only.
